# Skill Authoring — junit-mockito-agent

Canonical guide for creating new `SKILL.md` files in this test-generation agent.

---

## 1. Agent anatomy

```
.github/
├── copilot-instructions.md          ← always-on context (project, stack, conventions)
├── agents/
│   ├── test-convention-learner.agent.md   ← analyzes existing tests → generates skills
│   └── test-generator.agent.md            ← reads a skill and writes the tests
├── prompts/
│   └── learn-test-conventions.prompt.md
└── skills/
    ├── java-junit/SKILL.md                ← pure JUnit 5 best practices
    ├── junit5-springboot-defaults/SKILL.md ← default conventions (fallback)
    ├── test-services/SKILL.md             ← generated by Convention Learner
    ├── test-controllers/SKILL.md          ← generated by Convention Learner
    ├── test-repositories/SKILL.md         ← generated by Convention Learner
    ├── test-use-cases/SKILL.md            ← generated by Convention Learner
    ├── test-integration/SKILL.md          ← generated by Convention Learner
    └── create-skill/SKILL.md              ← this file
```

**Key rule**: every `SKILL.md` lives at `.github/skills/<name>/SKILL.md`.
The folder name must match the `name` field in the frontmatter exactly.

---

## 2. Required SKILL.md structure

```markdown
---
name: <slug-in-kebab-case>
description: "Use when: <trigger phrases separated by semicolons>."
user-invocable: true # omit or set false if only loaded internally by agents
---

# Skill Title

One-line description: what this skill does and what it is for.

---

## Section 1: ...

## Section 2: ...
```

### Frontmatter — fields and rules

| Field            | Required | Notes                                                                 |
| ---------------- | -------- | --------------------------------------------------------------------- |
| `name`           | Yes      | Must match the folder name. kebab-case.                               |
| `description`    | Yes      | **This is the discovery surface.** Include activation phrases.        |
| `user-invocable` | No       | `false` if the skill is only loaded by agents (e.g. via `read_file`). |

### The `description` is the most important field

The agent decides whether to load a skill **solely** based on this string.
Use the pattern `"Use when: <case A>; <case B>; <keywords>."`:

```yaml
# GOOD — rich in activation phrases
description: "Use when: writing tests for @Service classes; mocking repositories; unit testing business logic; service layer tests."

# BAD — too generic
description: "Tests for services."
```

## 3. Skill types in this agent

### 3a. Test convention skills (primary type)

Generated by `test-convention-learner` and consumed by `test-generator`.
One skill per Spring Boot component type:

| Slug                | Component covered                                        |
| ------------------- | -------------------------------------------------------- |
| `test-services`     | `@Service`, `@Component` — pure Mockito unit tests       |
| `test-use-cases`    | Classes with `UseCase`, `Command`, `Handler` in the name |
| `test-controllers`  | `@RestController` — tests with `@WebMvcTest` / `MockMvc` |
| `test-repositories` | `@Repository`, `JpaRepository` — `@DataJpaTest`          |
| `test-integration`  | `@SpringBootTest` — full integration tests               |

### 3b. Cross-cutting best practice skills

Like `java-junit`: general rules applicable to any test.
Loaded manually or as a fallback.

### 3c. Procedural skills (like this one)

Workflow guides for the agent itself (how to create skills, how to configure the project, etc.).

## 4. Minimum content for a test convention skill

Every test-type skill MUST include the following sections:

```markdown
## Test class setup

<!-- Annotations, extensions, @Mock / @MockBean, @InjectMocks -->

## Test method naming

<!-- Exact pattern: should_X_when_Y, givenX_whenY_thenZ, etc. -->

## Assertion library

<!-- AssertJ (`assertThat`), JUnit (`assertEquals`), Hamcrest -->

## Mocking style

<!-- BDDMockito (given/willReturn), classic Mockito (when/thenReturn) -->

## Fixture / test data setup

<!-- @BeforeEach, builders, factory methods, new Object() -->

## Exception testing

<!-- assertThrows, BDDAssertions.thenThrownBy -->

## File placement

<!-- src/test/java/<same-package>/ClassNameTest.java -->

## Full example

<!-- A real test example extracted from the project -->
```

## 5. How test-generator uses skills

The `test-generator.agent.md` follows this flow:

```
1. Detects the component type (@Service, @RestController, etc.)
2. Looks for: .github/skills/test-<type>/SKILL.md
3. If found → reads it with read_file and applies ALL conventions
4. If not found → falls back to .github/skills/junit5-springboot-defaults/SKILL.md
```

**Implication**: if you create a test convention skill, the agent will use it **automatically**
as long as the slug matches one of the recognized slugs in the table in section 3a.

## 6. Step-by-step creation process

### Step 1 — Choose the type and slug

Determine what type of skill you are creating and pick the correct slug from the table in section 3.

### Step 2 — Create the folder and file

```
.github/skills/<slug>/SKILL.md
```

### Step 3 — Write the frontmatter

```yaml
---
name: <slug>
description: "Use when: <3-5 specific activation phrases>."
---
```

### Step 4 — Write the skill content

- For test convention skills: include **all** sections from section 4.
- For cross-cutting skills: describe rules, anti-patterns, and examples.
- For procedural skills: describe the workflow step by step (like this file).

**Writing rules**:

- Be explicit and prescriptive — the agent will follow instructions to the letter
- Include real code examples extracted from the project, not invented ones
- Specify what to do AND what NOT to do
- Use tables for conventions that have multiple cases

### Step 5 — Verify auto-discovery

VS Code Copilot **automatically discovers** all `SKILL.md` files located at:

```
.github/skills/<name>/SKILL.md
```

No manual registration in `copilot-instructions.md` is required.
The skill will appear in the agent context in the next chat session.

> **Verification**: if the skill does not appear, check that the folder name matches the `name`
> field in the frontmatter and that the file is named exactly `SKILL.md`.

### Step 6 — Validate

Check:

- [ ] The folder name matches the `name` field
- [ ] The `description` contains specific activation phrases
- [ ] The frontmatter is valid YAML (no tabs, quotes around values that contain colons)
- [ ] The content covers all cases the agent needs
- [ ] The file is named exactly `SKILL.md` (case-sensitive)

---

## 7. Anti-patterns — what NOT to do

| Anti-pattern                         | Problem                                                        | Solution                                  |
| ------------------------------------ | -------------------------------------------------------------- | ----------------------------------------- |
| Generic `description`                | The agent does not load it when relevant                       | Add specific activation phrases           |
| Slug ≠ folder name                   | Silent failure when trying to load the skill                   | Keep folder name and `name` field in sync |
| Invented code examples               | The agent applies conventions that do not exist in the project | Extract real examples from `src/test/`    |
| Mixed conventions for multiple types | The agent applies wrong rules to the wrong component type      | One skill per component type              |
| Tabs in YAML frontmatter             | Silent parse failure                                           | Use spaces only                           |
| File not named `SKILL.md`            | Not auto-discovered by VS Code Copilot                         | The file must be named exactly `SKILL.md` |
